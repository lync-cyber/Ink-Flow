把 LLM 嵌进人形机器人上肢：3 层能用，2 层会炸

TL；DR LLM 的 token 串行解码决定它进不了 10 ms 级实时控制环。能落地的只有任务级、监督级、离线参数建议三层——闭环控制和安全联锁层必须隔离。

时延这一关没法绕

我们在一台双臂 7 自由度的人形上做 LLM 辅助控制，底层 FOC 控制器，电流环跑 1 kHz、速度环 500 Hz、位置环 100 Hz。第一天架构师画的图里 LLM 被拉到了位置环旁边做"在线修正"，第一周就被现实打回。

最快的本地推理链路（7B 量化 + CPU），首 token 180 ms，完整输出 900 ms。100 Hz 位置环的周期是 10 ms。意味着模型还没吐完一个字，位置环已经转了 90 个周期。

模型越强，越要把它关在只读的笼子里。

在安全等级要求 Cat.3 PL=d 以上的机械臂回路里，任何非确定性计算必须被隔离在安全控制器之外1。

ISO 10218-1:2011 §5.4

这不是"我们的工程慢"，是物理规律：LLM 的 token 串行解码决定它进不了控制环。参考 Attention Is All You Need 里提到的串行解码链路——这是结构性限制，不是工程能优化掉的。

能用的三层，按频率排

把 LLM 接进去的正确姿势是按频率垂直分层：

  1. 任务级（0.1–1 Hz 以下）——接自然语言任务，分解为动作序列，输出 JSON 轨迹草稿。每个动作节点 3–10 秒执行时间，LLM 延迟在这里是噪声。
  2. 监督级（事件驱动）——电流异常、碰撞、力矩阈值超限时，把前后 5 秒的传感器快照喂给 LLM 做归因。延迟 1 秒完全可接受，人工响应至少 5 秒。
  3. 参数建议级（离线）——工况结束后，把 PID 参数、负载、轨迹误差丢给 LLM 给调参建议。这一层只写报告，不改参数。

典型的分层调度骨架

python 
async def task_loop():
    plan = await llm_plan(user_request)     # 0.5-3s, 允许
    for step in plan.steps:
        traj = motion_planner(step)          # 10-50ms, 本地
        await realtime_executor.run(traj)    # 1ms 周期, FOC 走 C++

async def on_fault(fault_event):            # 事件触发
    root_cause = await llm_diagnose(fault_event.snapshot)
    dashboard.push(root_cause)               # 只显示，不改控制

调试时可以 Ctrl+C 中断 task_loop 但不会影响底层 FOC——实时层跑在独立进程。这三层之外的都别碰。

LLM 调参建议 vs 台架实测（空载 → 10 kg 负载）

参数 LLM 推荐 台架实测可用 现象（用 LLM 值时）
kp 3.8 2.4 加负载后电流环振荡，波形锯齿
ki 450 180 积分饱和，启停抖动
ff_gain （未提） 0.7 轨迹滞后 30 ms 以上
Note

LLM 从论坛学来的"通用建议"不承载具体电机的电感 Ls、转子惯量 Jm、编码器分辨率——这些必须在台架上辨识，不能靠推理。

图 1 · LLM 在机器人栈中的分层位置

会炸的两层

  • 电流环 / 速度环 / 位置环本身——时延和确定性双重不兼容。用 LLM 替换 PID 是学术 PoC，现场一次就能把减速器打坏。
  • 安全联锁层——急停、碰撞停机、关节限位。任何 ML 模型（包括 1B 以下的小模型）都不应出现在这条链路上2。
Tip

排查 LLM 误建议时，优先看它有没有拿到本台设备的辨识报告——没有的话，所有参数建议都按"未经验证"处理。

一个具体的踩坑：LLM 生成电机调参的幻觉

第二个月想偷懒，让 LLM 读 motor_params.yaml 给新负载推荐 PI 参数：

yaml 
current_loop:
  kp: 2.4        # LLM 给的是 3.8
  ki: 180        # LLM 给的是 450
  ff_gain: 0.7   # LLM 直接没提

LLM 推的 kp=3.8 空载看着还行，一加负载直接电流环振荡，示波器上电流波形变成锯齿。之前 GPT-3.5 也给过类似建议，换 GPT-4o 没本质改善——因为缺的不是模型能力，是设备辨识数据。

小结：这一层的红线

LLM 只能读历史数据，推理完必须标注"需在实验台架验证"，不得直接写回 motor_params.yaml。相关标准参考国标 GB/T 38369 机器人安全规范（公众号内链示例）。

Warning · 不要做这件事

永远不要让 LLM 直接写回生产环境的 motor_params.yaml、安全联锁表、报警阈值配置——任何参数写回必须经过台架验证 + 人工签字 + 版本化。

给同行的 7 条铁律

实操上我们守着这 7 条，已确认能守住的打勾：

  • 推理延迟 > 10 ms 的模型，永远不进实时控制环
  • 任何控制参数的写回必须经过台架验证 + 人工签字
  • 安全联锁链路上不出现任何 ML 组件
  • LLM 调用日志落盘 180 天
  • 报警归因的 top-1 置信度阈值仍在调整
  • 多机协同场景下的 LLM 冲突仲裁还没定方案
  • 视觉模型（VLM）的边界红线还没写进规范
附：三个会被立刻叫停的场景
  • 让 LLM 直接驱动 DO 点位输出
  • 用 VLM 做人员闯入检测替代安全光栅
  • 把模型推理结果写入 PLC 寄存器
  1. ISO 10218-1:2011 是工业机器人安全通用规范，Cat.3 PL=d 对应 IEC 61508 的 SIL-2 等价要求。
  2. ISO 13849-1 附录 D 明确排除非确定性计算组件进入安全功能链路——这个在论证阶段是直接扣分项。
